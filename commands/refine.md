# /refine — Refinement Pipeline from Requirements to Tickets and Changes

Take a **raw business or feature request** all the way to **implementation tickets and OpenSpec changes**.

## 🚦 Two Refinement Modes (Dan North / Liz Keogh Principle)

Not every requirement needs 7 stages and multiple UML diagrams. This command offers **two speeds**:

| Mode | When to Use | What It Produces | Effort |
|---|---|---|---|
| **Standard Mode (Fast-Track BDD)** *(Default for standard features and regular tickets)* | Standard business tickets, policy changes, additions to existing domains. | 1 Three Amigos / Example Mapping session: INVEST Story + Invariant Rules + SBE Example Tables with concrete data + Red Questions. Directly generates the OpenSpec change (`proposal`, `design`, `tasks`, `spec delta`). | 1 Approval Gate. Ready in minutes. |
| **Deep Mode (7 stages)** *(Activated with `--deep` or when there are > 3 complex use cases)* | Large specification documents, completely new modules, or workflows with high concurrent/asynchronous complexity. | Full formal 7-stage chain: inventory, validated Cockburn use cases, validated UML sequence diagrams, stories, and tickets. | 7 Sequential Approval Gates. |

---

## The Core Rule of This Command

🔴 **In Standard Mode:** Present the complete Example Mapping matrix (Rules, Concrete Examples, Knowledge Gaps) and ask for approval in a **single GATE** before generating OpenSpec artifacts.

🔴 **In Deep Mode:** **Before each of the seven stages, stop and ask for explicit approval.** No exceptions for small stages or simple requirements. The user must be able to open the file generated by the previous stage and review it before approving the next one.

🔴 **No stage runs on input that was not verified on disk.** The file must exist, and if the stage had a validator, its verdict must be approved.

---

### Standard Mode — Fast Flow (Three Amigos Example Mapping)

If `--deep` is not specified and the requirement has a clear, focused scope:
1. **Step 0 — Framing:** Resolve `<ID>` (`TK-<NNNNN>` or `REQ-<YYYY-MM-DD>-<slug>`) and `<slug>`.
2. **Step 1 — Example Mapping:** Dispatch the `functional-analyst` agent to perform Example Mapping and rule refinement:
   - Extract the INVEST Story.
   - Distill invariant Business Rules.
   - Build the **SBE Example Table with concrete data** (inputs, preconditions, expected outputs).
   - Identify Red Cards (open questions and ambiguities).
3. **⛔ Approval GATE:** Present the result to the user.
4. **OpenSpec Generation:** Once approved, directly create `openspec/changes/<ID>-<slug>/` with:
   - `proposal.md`: Why, what changes, and new capabilities (includes the INVEST story from Step 2).
   - `specs/<domain>/spec.md`: Specification delta with the SBE table.
   - `tasks.md`: Atomic TDD task list.
   - `design.md`: Architecture and design decisions.
5. **Register in the unified index**, exactly as `/change propose` does: append a row to `docs/tickets/README.md` for `tasks.md` (`Track: refine`, `Status: proposed`), and to `docs/stories/README.md` — pointing at `stories.md` if the package includes one, otherwise at `proposal.md`'s story section.
6. Ready for `/feature` or `/change apply` to begin TDD implementation.

### Deep Mode — The Seven Formal Stages

| # | Subagent (`name`) | Definition | Input | Writes To |
|---|---|---|---|---|
| 0 | `requirement-enumerator` | `agents/product-agent/00-requirement-enumerator.md` | Raw requirement | `docs/diagrams/use-cases/<ID>-requirement-inventory.md` |
| 1 | `use-case-generator` | `agents/product-agent/01-use-case-generator.md` | Inventory + cross-checks from stage 0 | `docs/diagrams/use-cases/<ID>-<slug>.md` |
| 2 | `cockburn-validator` | `agents/product-agent/02-cockburn-validator.md` | Use cases from stage 1 | `docs/diagrams/use-cases/<ID>-cockburn-validation-report.md` |
| 3 | `diagram-generator` | `agents/product-agent/03-diagram-generator.md` | **Validated** use cases + existing codebase | `docs/diagrams/sequence/<ID>/<ID>-sequence-diagrams.md` |
| 4 | `diagram-validator` | `agents/product-agent/04-diagram-validator.md` | Diagrams from stage 3 + validated use cases | `docs/diagrams/sequence/<ID>/<ID>-diagram-validation-report.md` |
| 5 | `invest-stories` | `agents/product-agent/05-invest-stories.md` | Validated use cases and sequence diagrams | `docs/stories/<ID>-<slug>.md` |
| 6 | `ticket-generator` | `agents/product-agent/06-ticket-generator.md` | Stories from stage 5 | `docs/tickets/<PREFIX>-<NN>-<slug>.md` + `docs/tickets/README.md` + **`openspec/changes/<slug>/` per story with implementation tickets** |

All output paths are relative to the project root.

🔴 **Stages 3 and 4 write to `docs/diagrams/sequence/<ID>/`** — a dedicated subfolder per requirement, which **you must create** before dispatching stage 3 if it does not already exist.

## Step 0 — Framing (Before Stage 0)

1. **Resolve `<ID>`**: `<TICKET-ID>` if the requirement has an issue tracker number, otherwise `REQ-<YYYY-MM-DD>-<slug>`. **The same `<ID>` is used across all seven stages** in all file names.
2. **Resolve `<slug>`**: Short kebab-case describing the requirement goal.
3. **Check for previous work** with that `<ID>` in the four output folders. If found, report it and ask whether to resume or start fresh. **Do not overwrite an existing artifact without permission.**
4. Show the framing summary and **ask for the first OK**.

## The Gate Protocol (Identical Across All Seven Stages)

**Before** dispatching stage `<N>`:

```
⛔ GATE — Stage <N>: <stage name>

About to dispatch : <subagent name>
With this input   : <file(s) from previous stage, verified on disk>
Will write to     : <exact path>
What it will do   : <one or two lines>

Previous stage status:
- <file> — exists ✅ / missing ⛔
- <validator verdict, if applicable>
- Knowledge gap log: <N open gaps>

Proceed? (yes / no / fix <what>)
```

**Wait for the response.** `no` halts the chain and nothing is dispatched. `fix <what>` sends instructions back to the generator of that stage in correction mode, not to the validator.

**After** the stage finishes:

```
✅ Stage <N> completed — <subagent name>

Written to : <exact path>   ← open and review before approving the next stage
Summary    : <3-5 lines from subagent report>
Blockers   : <none | list>
Gaps       : <N open, which ones were closed and how>
```

⚠️ **The path you report must be verified on disk.** If the subagent reports that it wrote the file but the file does not exist, that is a stage failure: report it and do not advance.

## Stage Preconditions (Verification Before Dispatch)

| Stage | Do Not Start Until… |
|---|---|
| 0 | Requirement text and `<ID>` are present; user approved the framing. |
| 1 | Stage 0 inventory exists · **no blockers** · primary actor is selected and justified. |
| 2 | Use case document exists · includes ID inventory as first section · **ends with coverage matrix**. |
| 3 | Cockburn report says **APPROVED** or **APPROVED WITH OBSERVATIONS** (with observations declared) · `docs/diagrams/sequence/<ID>/` exists. |
| 4 | Diagram file exists · **every diagram renders** (a diagram that fails to parse must be fixed, not validated). |
| 5 | V1–V5 validation report does **not** say `INVALID` or `INCONSISTENT`. |
| 6 | Stories file exists · **closes with coverage matrix against stage 0 IDs**, not against use cases. |

## The Two Correction Loops

```
0 ──► 1 ──► 2 ──┐        3 ──► 4 ──┐
      ▲         │        ▲         │
      └─fix─────┘        └─fix─────┘
```

- **Validators do not fix.** Stages 2 and 4 issue reports and return control; fixes are made by the generator (1 or 3) in *correction mode*. A generator that self-validates is not an independent check.
- **Maximum 3 iterations** per validation. On the third failure, **stop and notify** the user — do not keep looping automatically.
- **Each iteration goes through its gate**: tell the user what failed, what will be corrected, and with which agent.
- **In stage 2, evaluate A2 (primary actor) first.** If the primary actor is wrong, B1 and B2 fail in cascade and the rest of the report is noise: fix A2 first and revalidate.
- **In stage 4, if the report returns V1 findings**, the issue is usually in prompt 03, not in the diagram itself. Take note: it means a construction rule was stated unclearly.
- **If stage 2 renumbers or reclassifies use cases, sequence diagrams are reviewed, not blindly renamed.**

## What You Track End-to-End

**The Knowledge Gap Log (Registro de huecos).** Starts in stage 0 and travels through stage 6. Display it at **every** gate.

| ID | Gap / Open Decision | Stage Where It Emerged | Who Closes It | Status |
|:-- |:-- |:-- |:-- |:-- |

- A gap is **never closed by guessing**: it is closed by a business answer, a third-party response, or codebase verification. Always record **which of the three closed it**.
- Any gaps still open at the end **become Block 0 tickets** in stage 6: each `⚠️` appears as a `Spike` or `Administrative Task`, never diluted into a vague note. An undefined acceptance criterion must not produce an implementation ticket.

**The Coverage Matrix against the SOURCE.** Artifacts from stages 1, 5, and 6 must end with their coverage matrix against stage 0 IDs — **not** against the previous link in the chain. Validation subagents catch **fabrication**; **none catch omission**. Without this rule, a requirement dropped in stage 1 will not be noticed later. **Verify this matrix at every gate**; do not assume the subagent included it.

---

## Stop-the-Line Conditions

Stop the chain immediately, report, and **wait for user guidance** if:

- Stage 0 marks **at least one blocker** (an ID that contradicts the codebase or cannot be implemented as requested).
- A validation **does not converge within 3 iterations**.
- The requirement **contradicts a living spec** in `openspec/specs/`.
- A subagent reports that a file was written, but the file is missing from disk.

Stopping is not a failure: continuing to document something that is already broken is.

---

## Closing Summary

When stage 6 completes and the user approves it, present the **pipeline summary report**:

```
## Pipeline Completed — <ID>

| Stage | Artifact | Path |
|---|---|---|
| 0 … 6 | … | … |

## Traceability
Requirement (N IDs) → Use Cases (N) → Stories (N) → Tickets (N)

## Coverage Against Source
- Covered IDs: N of N
- <any IDs NOT covered and explanation>

## Knowledge Gap Log — Final State
| ID | Gap | Who Closes It | Block 0 Ticket |

## Questions for Stakeholders / Business
1. <question> — blocks: <what>
```

🔑 **Stage 6 also opens the OpenSpec change for each story**. A ticket without an OpenSpec change is an orphaned task: it gets implemented and closed, but the living domain spec is never updated. Changes start in **`propose`**, so each one requires **its own gate** before code is touched. A story whose tickets are all `Spike` or `Administrative Task` **does not open an OpenSpec change**, and the report should state this clearly.

**The pipeline ends with tickets and their OpenSpec changes.** Implementation is handled by `/feature`, ticket by ticket, **inside** the change that groups it.

---

## Constraints

- **The pipeline produces documentation, not code.** Do not modify application source code, views, or execute database mutations. The output is **additive**, under `docs/` and `openspec/`.
- **Each agent is dispatched with scoped context**: only the artifacts it needs, not the entire conversation history.
- **Each agent prompt is applied verbatim** from its file. Its internal constraints override any shortcuts suggested here.
- **Do not mix frameworks:** stage 2 adheres strictly to Cockburn and Larman; stage 4 to UML and consistency; stage 5 to INVEST and BDD.
- **No stage should demand features or patterns that the project stack does not support** (respecting framework versions, language level, and architectural patterns defined in `project.md`).
- **Do not skip gates.** If the user asks to run continuously, offer `--without-gates` as an **explicit opt-in** and warn that they lose the low-cost inspection point: from stage 5 onward, misunderstandings have already propagated to stories and tickets. **Never make this the default.**
- Use a single, consistent `<ID>` across all seven stages.
